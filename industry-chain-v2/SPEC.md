# 产业链研究分支 v2 — 产品/工序优先的产业链建模

## 1. 产品概述

- 产品名：产业链研究分支 v2
- 阶段：MVP / 光模块行业试点
- 目标用户：需要在 10 分钟内理解产业结构、关键节点与研究缺口的研究员
- 解决的问题：现有流程从上市公司披露与供货边出发，能核验“关系是否真实”，但不能先验保证“产业由什么组成、节点为何重要、哪些空白必须继续研究”。

本分支与现有关系台账并行，不覆盖 `output/nodes.csv`、`output/edges.csv`。现有证据边作为商业关系观察层的候选输入，不能反向定义产品/BOM骨架。

## 2. 目标与范围

### 目标

1. 自上而下定义应用场景、产品路线、功能、部件/材料、制造工序与设备类别。
2. 明确区分结构节点、公司实体、能力映射与商业供货观察。
3. 为每个结构节点给出重要性判定及依据状态，禁止无依据的伪精确评分。
4. 生成结构空白、玩家空白、能力空白、关系空白、时效空白的研究队列。
5. 提供可运行校验器与简洁读者输出。

### MVP范围

- 行业：光模块及其上游材料、芯片、部件、制造工序与设备。
- 样板路线：
  - 800G DR8 可插拔直检模块；
  - 800G 2×FR4 可插拔直检模块；
  - 400ZR 相干可插拔模块；
  - 1.6T 路线只登记为下一轮扩展，不在本轮假装填满。
- 公司映射只做足以证明 schema 与缺口机制可运行的最小样本。

### 非目标

- 不追求公司名单最多或供货边最多。
- 不把“未找到关系”解释为“不存在关系”。
- 不自动生成投资评级、交易建议或行业瓶颈结论。
- 不在本轮迁移全部 236 条历史边。
- 不重做现有证据核查 SOP。

### 成功标准

1. 三条样板路线均能从应用场景追到功能、部件/材料、工序与设备类别。
2. `Testing`、`CPO`、`COB`、`Silicon Photonics` 等不同概念不会混入同一类型轴。
3. 每个关键结构节点都有重要性类别、判定依据状态与缺口状态。
4. “结构存在证据”“公司能力证据”“供货关系证据”三类证据严格分离。
5. 校验器能机械拦截：孤儿节点、非法关系、混层、无依据升格、缺口消失、无效URL、重复ID。
6. 读者页能在 10 分钟内回答：产业由什么组成、三条路线差异、关键节点、P0缺口。

## 4. 核心工作流

### 4.1 研究设计

- 触发：新行业或新产品路线立项。
- 用户动作：确定应用、产品、地域、时间范围与核心问题。
- 系统动作：建立路线记录和理论节点树。
- 结束条件：范围冻结，未纳入内容进入 `out_of_scope`。

### 4.2 产业拆解

- 顺序：应用场景 → 产品路线 → 功能 → 部件/材料，与制造工序/设备平行展开。
- 禁止：从公司名单反推产业必需节点；把工序、架构、材料、部件混为同类。
- 结束条件：每条路线的必需功能均映射至至少一个部件或明确缺口。

### 4.3 玩家与能力映射

- 公司是独立组织实体，不是结构节点的文本属性。
- 一家公司可以映射多个节点；每条能力映射必须说明 `生产中/拟生产/研发中/代理/未知`。
- 结束条件：关键节点已映射代表玩家，或生成玩家空白。

### 4.4 商业关系叠加

- 历史供货边只进入 `trade_observations`。
- 关系证据不得升级结构节点或公司能力状态。
- 结束条件：有证据则展示；无证据保持关系空白。

### 4.5 缺口队列

- 系统对每个结构节点生成五类覆盖检查。
- 缺口状态：`identified → scoped → researching → evidenced → resolved`；
  可转为 `blocked` 或 `out_of_scope`。
- 待研究项不得因无新证据从分母消失。

## 5. 数据源与字段设计

### 5.1 三种证据用途

| 用途 | 回答的问题 | 典型来源 |
|---|---|---|
| structure | 产业理论上由什么组成 | 标准、规范、技术白皮书、教材、官方技术文档 |
| capability | 某公司在某节点做什么 | 公司产品页、招股书、年报业务章节、认证与专利 |
| trade | 谁给谁供货 | 强制披露、合同/中标、双侧金额、现有证据边 |

证据用途不可替代：产品页可以证明能力，不能自动证明供货；供货边可以证明交易，不能定义完整BOM。

### 5.2 Canonical 文件

| 文件 | 作用 |
|---|---|
| `data/structure_nodes.csv` | 应用、产品路线、功能、部件、材料、工序、设备类别 |
| `data/structure_edges.csv` | 结构关系与路线适用范围 |
| `data/organizations.csv` | 公司/机构实体 |
| `data/capabilities.csv` | 公司到结构节点的能力映射 |
| `data/trade_observations.csv` | 商业供货观察 |
| `data/evidence.csv` | 三类证据及用途 |
| `data/gaps.csv` | 研究缺口与状态 |

详细字段见 `schema/CONTRACT.md`。

## 6. 端到端系统流

```text
研究问题/范围
  → 产品路线
  → 功能与BOM ─────┐
  → 制造工序/设备 ─┤→ 结构节点图
                    ├→ 节点重要性
结构证据 ──────────┘

公司能力证据 → 组织实体 → 能力映射
交易证据 ─────────→ 商业关系观察

结构节点 × 能力映射 × 关系观察 × 时效
  → 缺口生成
  → 优先级裁决
  → 研究队列
  → 读者输出
```

## 7. 功能模块

| 模块 | 责任 |
|---|---|
| Ontology | 类型、节点、合法关系与路线范围 |
| Importance | 结构关键性、瓶颈假设、替代性与证据状态 |
| Coverage | 五类缺口及其分母 |
| Evidence | 用途、来源、引语、日期与判定 |
| Mapping | 公司能力与供货观察 |
| Validator | schema、引用、状态机、混层与完整性校验 |
| Renderer | 主图、路线对比、关键节点与P0缺口 |

## 8. 状态设计

### 8.1 结构节点

`proposed → admitted → verified → deprecated`

- `proposed`：候选概念；
- `admitted`：类型和定义通过审核；
- `verified`：至少一条 structure 用途证据；
- `deprecated`：被替代，保留迁移关系。

### 8.2 能力映射

`proposed → evidenced → reviewed → admitted / rejected / stale`

### 8.3 重要性

- `structural_critical`：该路线不可缺的功能/部件；
- `bottleneck_candidate`：有证据或明确假设指向性能、产能、功耗、良率瓶颈；
- `enabling`：支撑关键工序或性能；
- `supporting`：必要但非当前区分度来源；
- `unknown`：依据不足。

重要性类别与置信状态分开。`unknown` 不等于不重要。

## 9. 非功能要求

- Python 标准库优先；无必要不加依赖。
- 构建确定性：相同输入产生字节一致的派生数据。
- Canonical 数据只能由 Codex 集成；代理输出保留来源目录。
- 所有派生输出记录输入 SHA-256。
- 校验失败返回非零退出码。
- 不访问付费墙或绕过登录墙。

## 10. 验收门

### Gate 0：读者价值

不了解行业的读者能否在 10 分钟内说出三条产品路线、共同部件、差异部件、关键工序与前三项缺口。

### Gate 1：结构完整性

三条样板路线必须覆盖应用、功能、部件/材料、工序、设备五层；未知项以缺口存在，不能静默遗漏。

### Gate 2：模型纪律

类型、关系、证据用途与状态转换全部通过 validator；禁止混层和证据越权。

### Gate 3：关键节点

所有 `structural_critical` 或 `bottleneck_candidate` 节点必须带依据状态；假设必须标 `hypothesis`。

### Gate 4：缺口闭环

每个关键节点的五类覆盖均有结果；P0缺口有下一研究问题与完成条件。

### Gate 5：商业证据

公司能力与供货关系分别验收；无供货证据不得影响结构完整性判定。

## 11. 风险与开放问题

- 三条路线的技术细节可能随标准和代际变化，所有路线需带 `as_of`。
- 重要性判定容易退化成主观评分，必须保留维度与依据，不只给总分。
- 结构证据也必须有来源，不能把“常识”包装成已验证事实。
- 现有公司名称和关系端点尚无统一稳定ID，本轮只做适配样例。
- 1.6T、LPO、CPO作为后续路线，未经单独范围冻结不得混入MVP。

## 12. 开发交接

执行顺序：

1. Codex 冻结本 SPEC 与 schema。
2. Grok/Claude/HY3/Kimi 在独立目录并行开发。
3. Codex 逐包审查，拒收越界、混层与无证据升格。
4. Codex 集成 canonical 数据。
5. 运行 validator、缺口生成与读者页构建。
6. 用 Gate 0–5 终验并形成审核报告。
