# 海外电话会情报层 MVP

## 1. 产品概述

- 阶段：可运行 MVP，用真实小样验证价值，不预设长期 schema 已稳定。
- 用户：产业研究负责人。
- 问题：通过海外核心同业与下游公司的最近四个季度电话会，识别受限需求、关键节点、动态行业卡点、候选解法及公司进展，并与现有产业链能力点形成可追溯的潜在匹配。
- 定位：独立情报层。它生成假设与验证队列，不直接改变现有事实账本。

## 2. 目标与范围

### 目标

1. 建立“来源 → 原文/录音转录 → 原子陈述 → 主题/节点 → 跨公司验证 → 研究输出”的闭环。
2. 输出公司季度卡和跨公司议题矩阵。
3. 至少展示一条“受限需求 → 卡点 → 解法 → 国内公司潜在匹配 → 缺失证据”的完整链路。
4. 跟踪管理层前瞻表述及季间兑现事件。

### MVP 范围

- 公司类型：核心同业、上游使能方、系统设备商与下游验证方；允许加入现有公司宇宙之外的高信息密度公司。
- 当前公司池：Coherent、Lumentum、Applied Optoelectronics、Fabrinet、NVIDIA、Arista、Cisco、Meta，以及扩展层的 Broadcom、Marvell、Nokia、Ciena、MACOM、Credo。名单由数据文件控制。
- 时间：每家公司最近四个已披露季度；缺失必须显式登记原因。
- 信源：
  - A：公司官网或监管披露的 transcript、prepared remarks、正式附件；
  - B：公司官网公开录音的带时间戳转录；
  - C：可信第三方完整逐字稿。
- 公司官网署名技术博客可作为 A 级 `official_technical_blog` 来源，但作者角色必须
  记为 `corporate_author`，其 `technical_claim/technical_demo` 不能冒充管理层商业确认。
- SEC、交易所或其他法定披露平台直接托管的季度/年度报告与正式业绩公告记为
  A 级 `regulatory_filing`；它们不能被伪装成电话会问答。
- 季间官方公告、监管文件、正式产品发布与客户披露可作为承诺兑现验证源。
- 本地尽量保存合法取得的原始材料；不得绕过登录或付费限制；第三方全文缓存默认不提交 Git。

### 非目标

- 不修改 `tree.yaml`、`knowledge.yaml`、`points.csv`、`edges.csv`、`route_bom.csv`、`capability_details.csv` 或 `corpus/_frozen.csv`。
- 不把电话会陈述直接升级为公司能力点、供货边或产业结构事实。
- 不强制给整个行业一个统一阶段标签。
- 不做投资评级、交易建议或综合技术评分。
- 季度槽位登记与深度人工判定分开：14 家均登记四个季度，但材料可用不等于已经完成全文提取或电话会逐字稿覆盖。

## 3. 角色与权限

| 角色 | 职责 | 权限边界 |
|---|---|---|
| 研究负责人 | 决定公司池、主题和正式结论取舍 | 批准候选陈述进入正式账本及未来是否回写原系统 |
| 自动采集/提取器 | 登记来源、缓存公开材料、生成候选陈述 | 只能写候选状态；不能作正式行业判断 |
| 判定闸操作者 | 核对原话、说话人、季度、事件、节点映射 | 可将候选改为已审核或驳回 |
| 渲染器/校验器 | 检查引用闭合并生成读者输出 | 只读取 canonical 数据，不改变研究判断 |

## 4. 核心工作流

### 4.1 来源登记

触发：新增公司季度或兑现事件。登记公司、自然/财务季度、材料类型、信源等级、URL、本地路径、发布日期、访问日期、可用状态与缺失原因。结束条件：每个公司季度槽位有材料或显式缺失记录。

### 4.2 候选陈述提取与判定

原文切分为原子陈述，记录说话人及角色、短引文、段落/时间戳、事实/前瞻/分析师问题属性、事件类型和候选主题。自动结果为 `candidate`；人工核验后转为 `reviewed` 或 `rejected`。

### 4.3 双轨节点映射

- 能对应现有结构时，记录现有 `cell_id` 或 `route_id`。
- 无对应项时记录 `unmapped_theme` 及理由。
- 未映射主题只能生成结构修订候选，不能修改现有本体。

### 4.4 跨公司验证

围绕同一主题对齐供给方与下游方陈述，记录 `supports / contradicts / independent / same_source / insufficient`。至少一家供给方与一家下游方相互印证，才可形成路线级阶段或行业卡点判断。

### 4.5 承诺兑现

电话会前瞻陈述生成承诺记录；季间官方材料或后续电话会更新为 `pending / fulfilled / partially_fulfilled / delayed / withdrawn / not_observed`。`not_observed` 不等于未兑现。

### 4.6 输出

生成公司季度卡、跨公司议题矩阵、技术陈述—商业反馈及完整链路示例；同时生成
`out/panorama-intelligence.csv` 供 WorkBuddy HTML 可选投影。所有结论可反查来源、
短引文与定位；冲突、未知、缺席和未映射项必须显示。

## 5. 数据与字段

新增目录统一放在 `calls/`：

| 文件 | 用途 |
|---|---|
| `universe.csv` | 公司池、角色、纳入理由、启用状态 |
| `sources.csv` | 公司季度槽位、材料、等级、URL/本地锚、可用状态 |
| `claims.csv` | 原子陈述、说话人、引文、事件、事实属性、审核状态 |
| `themes.csv` | 受限需求、卡点、解法及未映射主题 |
| `validations.csv` | 陈述之间的支持、冲突和独立性 |
| `commitments.csv` | 前瞻承诺、期限、兑现证据与状态 |
| `solution_links.csv` | 卡点所需能力与现有能力点的潜在匹配及缺证 |
| `technology_feedback.csv` | 公司技术作者主张与管理层商业事实/前瞻之间的反馈状态 |
| `disclosures.csv` / `event_claims.csv` | 官网公告、博客等披露件及其人工锚定的原子主张 |
| `events.csv` / `event_evidence.csv` | 公司事件、成熟阶段、证据来源与独立性 |
| `company_candidates.csv` | 一手来源待核或已核、但尚未晋级季度/事件监控层的发现候选 |
| `company_tier_reviews.csv` | 候选最近正式披露的逐期晋级复核、信号强度与边界 |
| `watch_entities.csv` | 不承担四季度完整性、只按事件持续监控的组织 |
| `entity_relationships.csv` | 母子公司、品牌、并购、前身与业务承接的时态去重关系 |
| `raw/` | 可合法保存的原始材料；第三方全文缓存默认 Git 忽略 |
| `out/` | 派生报告，禁止作为事实源手改 |

最小数据血缘：每个正式 claim 必须有 `source_id`；每个 validation 必须引用两个有效 claim；每个 commitment 必须引用一个前瞻 claim，若状态不是 `pending/not_observed` 则必须有兑现来源；每个 solution link 必须引用 theme，并可选引用现有 `point_id`。

技术反馈采用同一 `theme_id` 的保守连接规则，不做隐式跨主题匹配。`pending` 可链接
管理层前瞻信号；`confirmed/partially_confirmed/contradicted` 必须链接已审核管理层事实。
`not_mentioned` 不得携带商业 claim，避免把沉默渲染成确认。

公司分层采用 `discovery candidate → watch entity / quarterly coverage company`。发现候选
不进入事件雷达或覆盖率；事件监控实体不承担四季度完整性；只有启用的季度覆盖公司才必须
恰好登记四个季度槽。品牌或被收购实体通过带生效时间的关系保存历史身份，不与母公司重复
计算公司数或来源独立性。候选晋级季度覆盖层前必须有两个不同正式披露期的
`company_tier_reviews`，且不能两期均为 `no_relevant_signal`；事件监控层仅要求已核一手
来源，不借用季度材料闸门，也不计入四季度覆盖率。

## 6. 分析纪律

### 行业阶段

只记录明确事件：`announced / sampling / qualifying / volume_order / first_shipment / ramping / scaled / delayed / withdrawn`。没有明确证据则为未知。需求侧与供给侧分开。

### 行业卡点与受限需求

行业卡点必须明确影响性能、功耗/散热、成本、良率/产能、可靠性/运维或标准/兼容/认证，并由两家独立公司或供需两侧相互印证。单家公司问题只能是公司级障碍。

因果链为：`应用需求 → 所需指标 → 关键节点 → 限制因素 → 受限结果 → 候选解法 → 进展/剩余缺口`。

卡点状态：`candidate → binding → solution_emerging → partially_relieved → industry_resolved → shifted`。单家公司成熟解决通常只能支持 `partially_relieved`；行业性解除还需供应/产能、客户采用、成本与可靠性均不再形成约束。

### 技术判断

可行性、稀缺性、可替代性分别记录，不合成总分。证据状态仅允许：`verified / partially_supported / company_claim_only / conflicting / insufficient`。

### 差异比较

仅在同代际、同应用、同形态之间比较；按架构、性能、可靠性/良率、成本、量产交付、商业适配六维记录。无共同基准的“领先/首创”只记公司主张。

### 显式关系事件

投资、收购与长期供应安排只能由明确披露建事件，主体、对手方、日期和证据 origin 分列。
`supply_chain_arrangement` 只接受已披露的长期供应协议、产能预留或正式采购安排；它不自动
生成 canonical 供货边，也不证明有效产能、实际采购或卡点解除。单方公告保持 `asserted`；
只有不同 origin 的对手方、监管材料或可观察结果支持后，才可提升为 `corroborated`。

### 国内公司潜在匹配

遵循：`节点重合 → 机理匹配 → 指标匹配 → 客户验证 → 量产验证`。只有节点重合时，不得表述为“解决卡点”。

## 7. 系统流与模块

```text
公司池/季度计划
  → 来源登记与合法缓存
  → 原文切分/候选陈述
  → 人工判定闸
  → 双轨节点映射
  → 跨公司验证/承诺兑现
  → 卡点与解法链
  → 公司季度卡/议题矩阵
```

MVP 模块：初始化/示例数据、CSV schema 校验器、报告渲染器、命令行入口和测试。网络搜索与自动转录可以保留清晰接口，不要求本轮集成付费服务。

## 8. 非功能要求

- Python 3，标准库优先；不得新增不必要依赖。
- 相同输入产生确定性输出。
- 所有正式结论可追溯到来源和定位。
- 不访问付费墙、不绕过登录、不伪造缺失材料。
- 不改现有 canonical 文件；测试应机械验证这一边界。
- 缺失、未知、冲突不能在渲染中消失。

## 9. MVP 验收

1. `calls/` 可独立运行校验与渲染，不依赖手改派生输出。
2. 至少包含真实公开来源构成的小样，而不是全虚构 fixture；样例明确标注来源等级和访问日期。
3. 至少生成两家公司季度卡、一个跨公司议题矩阵和一条完整卡点链。
4. 每条正式 claim 可追溯；分析师提问不能被渲染为管理层确认。
5. validator 能拦截断裂引用、非法枚举、缺失来源锚、兑现状态无证据、错误现有 point 引用。
6. `python3 scan.py --check` 仍通过，证明现有账本未被破坏。
7. README 给出一条命令完成校验和渲染，并说明如何继续补齐季度材料与事件证据。

## 10. 风险与开放问题

- 电话会信息密度不均，阶段可能长期未知。
- 第三方 transcript 的版权和可访问性不同，必须记录取得方式。
- 自动转录容易错认速率、金额和产品名，必须人工过闸。
- 下游客户可能只披露总资本开支，无法直接确认具体光技术路线。
- MVP 后再决定长期 schema、完整公司池、抓取调度和是否与每日更新机制接线。

## 11. 开发工包

实现方在 `calls/` 内维护 schema、validator、renderer、CLI、测试与真实样本；允许新增根 README 的简短入口，但不得修改现有 canonical 数据。Codex 负责审查契约符合性、运行测试、检查数据血缘与最终验收。
