# 光模块研究问题树 v2：双知识体系与 Why 关联

```
状态: 可开发
日期: 2026-08-23
阶段: 本地 MVP v2
关联: ADR-0009; CLAUDE.md; 问题队列 v1.3; 三段原始需求会话
```

## 1. 产品判断

当前 `out/问题队列.md` 是可信的 canonical 维护欠账，但不是用户要的研究入口。主产品必须从
“什么是光模块？”开始，让问题按理解依赖逐层生长，并明确区分两套知识：

1. **物理知识体系**：系统功能 → 组件 → 接口 → 制造工序 → 设备。
2. **技术路线体系**：系统需求/约束 → 正交选择轴 → 路线组合 → 所需能力 → 公司能力群。

两套体系之间不是第三棵知识树，而是一组 **Why 关联**：需求或瓶颈为什么导致某种工程选择，
该选择为什么改变某些组件、工序和设备，又为什么需要某类公司能力。

问题树只保存研究导航和回填合同，不保存事实答案。研究答案仍是可追加到现有
`knowledge.yaml` 的 YAML 条目；跨体系因果关系写入同一文件的 `why_links:`，不新建答案库。

三段 ChatGPT 会话只作为需求来源，不能作为事实锚。EML、SiPh、LPO、CPO、公司受益等具体
结论必须重新取得公开一手来源后才能进入 canonical。

## 2. 目标、范围与非目标

### 目标

- 新增一个从 `RQ000 什么是光模块？` 展开的、稳定 ID 的研究问题树。
- 明确展示物理知识和技术路线两条主干，Why 以跨主干关系显示。
- 每个问题显示回填目标、验收合同以及当前已关联 KN/WHY 数量。
- 所有研究回答都能形成 append-ready `knowledge.yaml` 补丁。
- 按实时 `tree.yaml`、`route_bom.csv`、`points.csv` 生成路线能力群快照。
- 严格分开“能力匹配候选群”和“路线级直接证据确认群”。
- 保留 `out/问题队列.md`，明确它是后台维护入口。

### 非目标

- 不自动用 LLM 生成无限问题，不为每个格机械复制几十个模板。
- 不把问题 YAML 当事实源，不自动把模型回答写入 canonical。
- 不把同格公司说成上下游，也不把能力匹配说成已服务某路线。
- 不在本轮重新研究或补写 EML/SiPh/CPO 等事实答案。
- 不迁移现有 KN、点、边、路线 BOM ID；旧 KN 保持兼容。
- 不解决路线份额、ASP、利润或投资收益；只保留这些层级所需的推论闸。

### 成功标准

- 用户打开一个文件即可看到根问题、两条主干和 Why 桥，不再面对 QA–QE 平铺表。
- 追加一个合法物理 KN 后，对应物理问题显示已覆盖。
- 追加一个合法路线 KN 后，对应路线问题显示已覆盖，并可形成路线直接证据公司群。
- 追加一个合法 Why 记录后，桥接问题显示已覆盖并展示完整因果链。
- 删除或写错任何引用时，`scan.py --check` 必须失败。
- 实时基线不写死：源 CSV/YAML 更新后重渲，问题覆盖和公司能力群同步更新。

## 3. 角色与闭环工作流

### 研究者

从 `out/研究问题树.md` 选择一个未覆盖问题，取得一手证据，提交 append-ready YAML 补丁。
研究者不能手改 `out/`，也不能用问题状态代替事实回填。

### 证据复核者

核对主张类型、原话、锚、适用条件、替代方案和公司归属；通过后才允许补丁进入
`knowledge.yaml`。能力匹配不能由复核者直接升级为路线服务证据，除非新增路线级直接锚。

### 渲染与校验系统

从 canonical 文件派生问题覆盖、路线能力群和实时基线；不做语义事实判断，只做引用闭合、
格式约束、确定性渲染和能力匹配推导。

### 闭环 A：物理知识

`选 PQ → 查一手来源 → 写物理 KN → 人工复核 → scan → render → PQ 显示已覆盖`

### 闭环 B：技术路线

`选 TQ → 分清选择轴/产品框架 → 查路线与公司直接证据 → 写路线 KN → 复核 → render`

### 闭环 C：Why 关联

`选 WQ → 写逐步因果链 → 每步标主张类型和证据 → 写 conditions/tradeoffs/alternatives → 复核 → render`

## 4. 数据来源与边界

| 数据 | 职责 | 不得推导 |
|---|---|---|
| `research_questions.yaml`（新增） | 问题父子关系、Why 桥、回填/验收合同 | 事实答案 |
| `tree.yaml` | 物理/供应链格坐标与骨架流向 | 具体产品一定采用某实现 |
| `knowledge.yaml.knowledge` | 有证据的物理知识或路线知识 | 无证据常识、聊天结论 |
| `knowledge.yaml.why_links`（新增顶层） | 跨体系的类型化因果链 | 技术成立直接跳公司受益 |
| `route_bom.csv` | 当前产品路线框架、选择轴文字与 BOM→格映射 | 唯一具体路线组合 |
| `points.csv` | 公司在物理格上的过闸能力点 | 路线采用、客户或供货关系 |
| `edges.csv` | 已核公司供货观察边 | 问题树父子关系、路线能力匹配 |
| `out/问题队列.md` | QA–QE 维护欠账 | 完整研究问题宇宙 |

实时基线在每次渲染时从上述文件重算，不在问题 YAML 写死公司数、KN 数、日期或问题覆盖数。

## 5. 问题树 canonical

新增根目录 `research_questions.yaml`，只装导航元数据：

```yaml
meta:
  version: v2
  root_id: RQ000
  answer_target: knowledge.yaml

questions:
  - id: RQ000
    parent_id:
    system: root
    order: 0
    question: 什么是光模块？
    writeback: knowledge
    acceptance: 有一条通过校验的 KN 显式关联本问题

why_questions:
  - id: WQ001
    order: 1
    route_question_ids: [TQ002, TQ003]
    physical_question_ids: [PQ001, PQ002]
    relation_type: need_to_constraint
    question: 系统需求为什么会变成这些物理约束？
    writeback: why_links
    acceptance: 有一条通过校验的 WHY 显式关联本问题
```

## 6. `knowledge.yaml` 回填合同

### 6.1 兼容策略

现有 KN 不迁移；缺少 `体系` 时按 `物理知识` 解释，缺少 `研究问题` 时仅表示尚未映射到问题树。
所有新回答建议显式填写：

```yaml
- id: KN###
  体系: 物理知识 | 技术路线
  研究问题: [PQ### | TQ### | RQ000]
  格: [cell_id]                 # 物理条目使用；路线条目可为空
  路线条目: [RB###]             # 技术路线条目使用
  标题: ...
  一句话: ...
  说细点: ...
  怎么用它判断: ...
  证据: [...]                   # 沿用现有五种锚型
  关联点: [P###]                # 可选；路线直接证据公司群从这里取公司
  录入日期: YYYY-MM-DD
```

规则：

- `体系=物理知识`：`研究问题`只能引用 RQ/PQ；如声明具体物理对象，`格`必须闭合到 `tree.yaml`。
- `体系=技术路线`：`研究问题`只能引用 RQ/TQ；`路线条目`至少一项且闭合到 `route_bom.csv`。
- 路线 KN 只有在自身证据明确联系公司与路线时，才可填写 `关联点` 并进入已确认服务群。
- `关联点` 必须引用真实 `points.csv.point_id`；同公司多个点在展示时去重。
- 研究问题覆盖只看 KN 的显式 `研究问题`，不从标题或聊天语义猜测。

### 6.2 Why 关联

`knowledge.yaml` 新增兼容顶层 `why_links: []`：

```yaml
why_links:
  - id: WHY###
    研究问题: WQ###
    路线条目: [RB###]
    物理格: [cell_id]
    因果链:
      - 顺序: 1
        层级: SystemNeed | Physics | Engineering | PhysicalDelta | Capability | CommercialAdoption | Economics | Investment
        主张类型: 事实 | 行业共识 | 工程推论 | 经济推论 | 投资假设
        陈述: ...
        证据引用: [KN### | RB###]
    条件: [...]
    取舍: [...]
    替代方案: [...]
```

规则：

- 每条至少两个有序步骤；顺序必须从 1 连续递增。
- 每步必须有主张类型、非空陈述和至少一个已存在的 KN/RB 证据引用。
- `路线条目`、`物理格`均至少一项并引用真实 ID。
- `研究问题`只能引用 WQ。
- `条件`、`取舍`、`替代方案`必须是列表且至少各一项，防止把工程推论写成必然结论。
- `Investment` 只能出现在 `CommercialAdoption` 与 `Economics` 之后；本轮不要求产生投资步骤。

## 7. 路线能力群视图

按 `route_bom.csv.产品路线` 聚合成当前“产品路线框架”，每条显示：

1. 应用边界与四个现有选择轴文字；明确这些字段可能列出多个兼容选择，不是唯一具体路线画像。
2. BOM 分组与映射的物理格。
3. **能力匹配候选群**：`route_bom.cell_ids × points.cell_id` 推导，按物理格列公司。
4. **路线直接证据确认群**：`体系=技术路线` 的 KN 同时关联该路线 RB 与真实 point 后得到。
5. 若不同产品路线得到相同候选群，显示“物理映射粒度不足以区分路线”，把差异留作 TQ010/TQ013。

任何候选群或确认群都不得表述为供应关系；公司供货只读 `edges.csv`。

## 8. 输出与页面结构

`render.py` 新增生成 `out/研究问题树.md`，顺序固定：

1. 边界声明：主研究导航，不是维护队列；回答回填 `knowledge.yaml`。
2. 实时基线：问题、KN、Why、格、路线框架、能力点计数。
3. 根问题与两条主干的缩进树；每个问题显示覆盖状态及关联 KN。
4. Why 桥问题及已验证 Why 链。
5. 路线能力群快照：候选群与确认群分栏。
6. 三种 append-ready YAML 模板：物理 KN、路线 KN、Why link。
7. 指向 `out/问题队列.md` 的后台维护入口说明。

不手改输出；`render.py --verify` 必须覆盖该文件。首版只生成 Markdown，不新增另一套网页。

## 9. 状态与更新规则

- **待研究**：没有 KN/WHY 显式引用该问题。
- **已覆盖**：至少一个通过不变量的 KN/WHY 显式引用该问题。
- **实时基线更新**：任何 canonical 输入变化后重跑 render 即更新；不设手工“刷新日期”字段。
- **问题扩容**：修改 `research_questions.yaml` 并升版本；不得由运行时 LLM 自由扩写。
- **答案更新**：追加或修订 `knowledge.yaml`，不能在问题 YAML 写答案。

“已覆盖”表示已有合格 canonical 条目，不表示该问题永远完结；事实变化仍通过知识条目版本与证据日期维护。

## 10. 校验与验收

`scan.py` 新增不变量⑭，至少检查：

- `research_questions.yaml` 可解析、表头结构正确、ID 唯一、唯一根为 RQ000。
- parent 引用闭合、无环、顺序稳定；PQ/TQ 只能挂在对应主干，WQ 两侧引用闭合。
- KN 的 `体系/研究问题/路线条目/关联点` 引用和类型闭合；旧 KN 兼容。
- WHY ID、WQ、RB、cell、证据引用闭合；因果链顺序与层级、主张类型合法。
- `Investment` 前必须出现 `CommercialAdoption` 与 `Economics`。
- 根目录白名单加入 `research_questions.yaml`。

`--selftest` 至少覆盖：正常问题树、重复 ID、悬空 parent、环、跨体系误挂、悬空 RB/cell/KN/point、
WHY 步骤乱序、空条件/取舍/替代、Investment 越级。

临时副本验收：

1. 基线渲染两次 SHA256 相同。
2. 追加合法物理 KN，目标 PQ 从待研究变已覆盖。
3. 追加合法路线 KN + 关联点，目标 TQ 变已覆盖且确认群出现对应公司。
4. 追加合法 WHY，目标 WQ 变已覆盖并展示链。
5. 制造一个悬空引用，`scan.py --check` 必须失败。
6. 真实工作区最终执行：

## 11. 风险与裁决

- `route_bom.csv` 当前是产品路线框架，不是完整正交组合；页面必须显式显示这个限制。
- 800G 与 1.6T 当前可能得到相同能力群，这是数据粒度信号，不准靠文案制造差异。
- 旧 KN 未映射研究问题时不会自动覆盖问题；后续可人工补 `研究问题`，不得用标题模糊匹配。
- Why 链一旦允许无条件或无替代路线，就会重演“技术成立→公司受益”的跳步；校验不得放松。
- 本轮不自动修改已有事实条目，也不从三段聊天抽取事实。
