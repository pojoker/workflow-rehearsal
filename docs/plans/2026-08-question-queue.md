# 问题队列设计方案（"问题树"的落地形态）

```
状态: 提案 v1.3（增加 canonical YAML 回填合同，未实施）
日期: 2026-08-22（v1.3 修订 2026-08-23，处置记录见 §10–§12）
关联: CLAUDE.md 纪律九条; render.py 页脚空叶格计数; docs/adr/0002（分层模型先例）; 三段原始需求会话（见 §11）
```

## 0. 一句话

问题不是需要手工种植的第二棵树，是账本的补集：**问题队列 = 脚本从现有账本派生的缺口清单**，
每条问题出生时带验收锚型，数据补上后下次重算自动销号。人只干两件事：从队首拿问题、裁决豁免。

问题队列也不是只读看板。每条问题必须显示 **回填目标**，研究或判定产物应直接形成 canonical
文件补丁，而不是停留在聊天或 Markdown 散文中。特别是 QB，交付物必须是可追加进现有
`knowledge.yaml` 顶层 `knowledge:` 列表的完整 KN 条目；需要在全景树显示反向索引时，再同步
对应 `tree.yaml` 叶格的 `knowledge_ids`。不新建答案 YAML，不复制第三份事实源。

这里的“问题队列”特指 **v1 canonical 账本维护欠账**，不是全部产业研究问题的宇宙。功能拆解、
部件制造、装配接口、正交技术路线和投资推论等原始愿景，只有在对应 canonical 结构存在后才能
继续派生；不得因为 v1 有五类问题，就宣称完整“问题树”已经落地。

## 1. 为什么不是第二棵树

三段原始会话把愿景说得更完整：从“光模块完成什么功能”出发，映射到部件；再追到每个部件
如何制造、部件之间如何装配、每个箭头需要什么设备；最后把光学平台、电接口、封装架构等
正交路线分开，并区分事实、工程推论、经济结果与投资假设。这个愿景成立，但它的正确形态
仍不是一棵手工维护的 yaml 树，理由三条：

1. **两个手工结构必然漂移。** tree.yaml 是唯一坐标系；问题若单独成树，每次 tree.yaml 升版
   都要人工同步问题树，漂移只是时间问题（两个 source of truth 反模式）。
2. **自由生成问题是噪音发生器。** LLM 生成一万个问题不要钱，判定才花 token（纪律2）。
   问题空间必须封闭：**问题 = 树坐标 × 固定模板**，扩模板须升版本号（同 universe 扩容规则）。
3. **问题只能从已存在的 canonical 坐标派生。** 当前 `tree.yaml` 遍历覆盖的是供给侧节点，
   `route_bom.csv` 覆盖部分正交产品轴；制造工序、装配接口和推论链尚无完整 canonical 结构。
   v1 先渲染现有账本补集，缺少坐标的研究问题留给后续 ADR，不能靠 LLM 临时补树。

## 2. 数据结构

### 2.1 派生问题（不落盘，每次重算）

五个发生器，全部从现有文件派生。question_id 由 (前缀, 现有ID) 决定性生成——同一缺口
跨会话重算得到同一 ID，人工裁决表才能对齐。

| 前缀 | 发生器（数据源） | 问题模板 | 回填目标 | 验收锚型 | 天然销号条件 |
|---|---|---|---|---|---|
| QA-{cell_id} | 空叶格（render.py 已算的 `empty` 集合） | 「{格名}谁在做？」 | `points.csv` | 自家披露件/互动易引语+锚（纪律1点锚规则） | 该格出现过闸点 |
| QB-{cell_id} | 有点但无 knowledge_ids 覆盖的叶格（render.py 已算的 `kbycell` 补集） | 「{格名}是干嘛的、为什么难、怎么判断谁够格？」 | `knowledge.yaml`；可选同步 `tree.yaml.knowledge_ids` | knowledge.yaml 锚型枚举（url/local_file/ledger_ref/search_protocol/web_snapshot） | 该格进入某条 KN 的`格`列表 |
| QC-{row_id} | shipments.csv 中 证据等级=C 且 `情景标记=base` 且校准三字段未齐且期间回算源已解锁的行（v1.2 收紧） | 「{公司}{期间}推断值该回算了吗？」 | `shipments.csv` | 新财报/海关月报锚（校准列三字段齐填） | 校准实际值/误差/校准日期三字段齐全 |
| QD-{hit_id} | triage.csv 中处置=待判的行 | 「{公司}+{格}判不判？」 | `triage.csv` | 处置枚举落定（已入点/驳回-*），驳回也是产出（纪律3） | 处置≠待判 |
| QE-{edge_id} | edges.csv 中验证状态不在已核白名单，或锚点为空的边（v1.2 收紧） | 「{供方}→{需方}这条边核过原文吗？」 | `edges.csv` | 验证状态更新为白名单内取值+锚 | 验证状态进入白名单且锚点非空 |

QB 的销号只表示“该格至少已有一条带锚知识”，不表示该格已经完整回答功能、材料、制造工序、
装配接口、设备、路线变化和投资影响。v1 不得把 `格 ∈ KN` 过度解释成完整知识卡验收。

QB 的回答合同不是自由文本摘要。研究者必须提交一个完整 KN YAML 补丁，字段至少与当前
`knowledge.yaml` 一致：`id`、`格`、`标题`、`一句话`、`说细点`、`怎么用它判断`、`证据`、
`录入日期`；每条证据至少含 `谁`、`原话`、`出处`、`锚型`、`锚`，锚型遵循不变量⑧。
`id` 在作答时按当时库内最大 KN 顺延，不能由问题队列提前固化。补丁经 `scan.py --check`
通过并追加到 `knowledge.yaml` 后，QB 由其 `格` 字段天然销号。`tree.yaml.knowledge_ids` 是展示
反向索引，不作为 QB 销号的第二口径；若同步，必须和新增 KN ID 一致。

QC 的"期间回算源已解锁"规则写死在 render.py：`{Y}年度`→次年5月1日（年报线），
`{Y}H1*`→同年9月1日（半年报线）；期间解析失败的行照常入队（fail-open，宁可多一条
问题，不许静默漏）。

QE 白名单为**逐字精确匹配**的已核取值清单，冻结在 render.py 内；任何新取值默认未验证
（fail-safe 方向：宁可多生成一条 QE，不许新状态静默算作已核）。改白名单记维护。
当前非白名单取值三种（实测 18 条边）：`本轮P2登记-待解匿`(13)、`本轮P1登记`(4)、
`待P2处理`(1)。

排序规则写死（人不排序，只从队首拿）：QD（发现成本已花，判定最贵）→ QA（结构缺口，
路线对比表中独有格优先于共用格）→ QB（机理缺口）→ QC（按期间早晚）→ QE。

### 2.2 人工裁决表 questions_manual.csv（唯一新落盘文件）

派生问题绝大多数靠"填格自动销号"，不需要人工关闭。只有两种情况需要落盘裁决：

```
question_id, 处置, 理由, 验收锚型, 双通道记录, 复核日期, 会话日期
```

- **处置=豁免**：该格结构性无解（如宇宙外私有主体无披露通道）。必填未来复核日期，
  到期自动重开——豁免是租的，不是买断的。
- **处置=真零**：检索过且确认无数据。必须走零结果双通道（纪律9）：双通道记录填
  两个独立通道的 search_protocol 锚（关键词/语料范围/检索日期/命中数 四键各一份），
  同样必填未来复核日期；今天的真零不能永久遮蔽未来披露。

裁决表不许出现"已回答"处置——回答问题的方式是往 points/knowledge/edges/shipments 里
写数据，不是在裁决表里打勾。数据是唯一事实（纪律6）。
QD 不得走人工裁决旁路，必须直接更新 `triage.csv` 处置，避免同一待判项出现两套状态。

## 3. 生成与渲染

- **并入 render.py，不建新脚本**（约 +60 行）：empty 集合、kbycell、csv 解析全部现成，
  第三个输出 `out/问题队列.md`（与 全景.md、知识库.md 并列）。手改 out/ 被拒，同现行规则。
- `out/问题队列.md` 顶部必须声明：v1 只展示当前 canonical 维护欠账；制造工序、装配接口、
  正交路线覆盖和投资推论尚未纳入，不等于完整研究问题空间。
- 每行新增“回填目标”列。页内增加“回填合同”短节，明确 QB 产物是可追加到
  `knowledge.yaml` 的完整 KN YAML 补丁，并列出必填字段与合法锚型；不能只交一段说明文字。
- 页脚追加一行：`问题队列=N条(QA:a QB:b QC:c QD:d QE:e) | 豁免x 真零y`。
  commit 信息的空格计数（纪律8）不变，问题总数可选附带。
- 若某条裁决指向已不存在的派生问题（格已填、豁免成了死重），渲染时列入页脚
  「待清理裁决」提示，人工删行。

## 4. 校验（scan.py 不变量⑬）

格式级检查，与⑪⑫同风格，不重算派生集：

1. question_id 前缀 ∈ {QA,QB,QC,QD,QE}，引用的 cell_id/row_id/hit_id 真实存在于对应文件，ID 不得重复；
2. 处置 ∈ {豁免, 真零}，QD 前缀不得进入人工裁决表；
3. 两类处置都必带未来复核日期，复核日期≤今天即报错（强制重开）；
4. 真零行的双通道记录必含两份 search_protocol 四键，序列化格式写死（v1.1，采纳评审 9.4），
   不变量⑬按结构解析，缺任一键即报错：

```
通道A{关键词=..;语料范围=..;检索日期=..;命中数=..}|通道B{关键词=..;语料范围=..;检索日期=..;命中数=..}
```

## 5. 与纪律九条逐条对齐

| 纪律 | 本方案 |
|---|---|
| 1 点先行序 | 不变。QA 的验收锚型就是点锚规则本身 |
| 2 token只花判定闸 | 发现（派生）与渲染全脚本；人只消费队首 |
| 3 会话末 --check | 新增不变量⑬进同一命令 |
| 5 禁并行迁移 | 零迁移：不动任何现有 schema 与 ID |
| 6 数据在csv | 唯一新数据文件 questions_manual.csv；队列本身是渲染 |
| 8 空格计数 | 空叶格口径不变，QA 与它同源 |
| 9 零结果双通道 | 直接编码进"真零"处置的必填字段 |

## 6. 边界：明确不做什么

- **不建第二棵树**，不引入 LLM 自由生成问题，模板五条封闭，扩模板须在本文档升版并记理由。
- **不建答案 YAML 中间库**。QA–QE 的完成结果直接进入表中列明的既有 canonical 文件；
  `out/问题队列.md` 只给回填合同和模板约束，不存答案。
- **需求侧问题不在 v1 范围**（谁买/为什么买/价格弹性）：现有坐标系是供给侧 BOM，
  物理根基对需求侧零解释力。需求侧要先扩坐标系（新的树层或独立轴），那是另一个 ADR，
  不许借问题队列夹带。
- **量化缺口发生器（"这个格出货量多大"）留给 v2**：全格铺开会瞬间生成大量低价值
  问题，先让现有推断行的校准闭环跑熟。（v1 原文误称 shipments 只覆盖少数格所以 QC
  体量小——实测 103 行，体量控制靠 §2.1 的 C 级基准行发生器定义，不靠覆盖面小。）
- **B 级直接披露行不生成 QC**：量价齐露行的推导即实际值，没有独立的回算对象；
  校准列的防腐设计（术语表：防止推断腐化成事实）只针对"事前估计、事后对账"的
  C 级行。情景行（D 级）的落地跟踪是另一类问题，v1 不入队。
- **制造工序与装配箭头问题不在 v1 范围**：当前 `tree.yaml` 是节点坐标，`flows` 是 BOM
  常识流向，不是可核验的制造接口账本。没有 component→process→equipment 和
  component→interface→component 的 canonical 结构，不能生成可自动销号的问题。
- **正交技术路线与推论链问题不在 v1 范围**：`route_bom.csv` 已分产品标准轴、电接口轴、
  封装架构轴和光子平台轴，但问题发生器尚未消费这些覆盖关系；Physics→Engineering→
  Economics→Investment 也没有类型化主张与前提链。二者都须另立 ADR 后再扩发生器。
- **三段会话只作为需求来源，不作为事实锚**：其中关于 EML、SiPh、CPO、POET、设备受益等
  内容不得直接写入 canonical。事实仍须回到公开一手资料并走现有锚型与判定闸。

3. `/Users/jowang/miniconda3/bin/python3 scan.py --check` 全绿；commit 记「维护:」或与当日产出合并记数。
4. 在临时副本中，为一个真实 QB 格追加一条满足不变量⑧的 KN 到 `knowledge.yaml`，重渲后对应
   QB 消失、总数减 1；真实 `knowledge.yaml` 不因验收发生变化。这个用例证明研究产物能补充
   原知识库 YAML，而不是只在队列中被手工勾掉。

验收标准：队列总数在页脚可见；填一个格（如任一 QD 落处置）后重跑 render.py，
对应问题自动消失，无需任何手工关闭动作。

## 9. 评审意见（2026-08-22，评审人已对照真实数据核实）

### 9.0 总体判断：方案成立，建议批准后实施

核心架构决策正确：「问题 = 账本的补集」消除了双 source of truth 漂移；确定性
question_id 使跨会话重算幂等、人工裁决表可对齐；出生即带验收锚型 + 数据补上自动
销号，把"问题"变成可机验的验收测试；豁免租约制与真零双通道把纪律9 从口头约束变成
schema 约束。与纪律九条的对齐是真实的。事实基础已核实：render.py 确有
`empty`/`kbycell`，scan.py 确有不变量⑪⑫与 --selftest 框架，三份 csv 字段与本文
描述一致。

### 9.1 必须修：QE 销号条件与 edges.csv 现实枚举不符（数据实证）

`验证状态` 是自由文本，现有 21 种取值；含"已验证"字样的仅约 13 条。而实质已核原文
的边——`v1.6r终验(单位感知重装)` 132 条、`正式版管线产出-人工原文复核通过` 10 条、
`本轮P1-SEC原文命中` 19 条等——均不含"已验证"三字。按 §2.1 的子串规则，236 条边中
约 190 条会生成 QE，队首被噪音淹没，直接违背"封闭问题空间"初衷。

**修法**：QE 发生器改用显式白名单枚举（本文档列死哪些取值算已验证，新取值默认未
验证），白名单写在 render.py 内；不为此给 edges.csv 加列（保持零迁移）。

### 9.2 必须修：QC 体量被低估（数据实证）

§6 称"shipments.csv 目前只覆盖 MOD 层少数格"，但实测 103 行中 102 行校准实际值为
空——首版渲染即产生约 102 条 QC。文档推迟的是量化缺口发生器，却未意识到 QC 发生器
本身就是大体量。

**修法**：QC 加触发闸——仅当「校准日期为空 **且** 对应期间已有新财报/海关数据可
得」时生成；未到回算时点的行不进队列。

### 9.3 体量实测（首版渲染预估）

| 发生器 | 预估条数 | 依据 |
|---|---|---|
| QA | 2 | 空叶格实测 2/40（M2c、EQ8） |
| QB | ≤26 | 40 叶格减知识覆盖 14 环节 |
| QC | ~102（修 9.2 后应大幅收缩） | 校准实际值空 102/103 行 |

### 11.1 需求来源

这些会话是产品需求与研究方法的来源，不是可承重事实语料。会话内的网页引用、行业结论和
公司判断若要进入账本，必须重新取得公开一手来源并按现有锚型核验。

### 11.2 提炼出的稳定需求

1. **研究顺序**：系统需求→功能→部件→制造工序→装配接口→设备；先理解产品，再比较路线。
2. **分类纪律**：产品标准、光器件、光子集成、电接口、封装架构、链路距离和制造设备是不同轴，
   不能把 EML、SiPh、LPO、CPO、POET、光耦合设备塞进一棵互斥分类树。
3. **两种“连接”分离**：信号如何流动，与工厂如何装配，是两套关系；供应链供货边又是第三套。
4. **证据纪律**：典型工艺不等于所有厂商都采用；技术解决问题不等于客户采用，更不等于公司
   受益。结论必须区分事实/行业共识/工程推论/经济结果/投资假设，并显式保留条件和替代路线。
5. **问题闭环**：每个问题都应带答案落盘位置与销号条件；没有 canonical 坐标的问题不能靠自由
   生成长期维护。

### 11.3 v1.2 裁决

- **五个发生器 QA–QE 不扩容**。它们只负责当前 canonical 账本维护欠账，仍可直接实施。
- **修正“完整映射”表述**。MOD 层 QB 和树遍历只能覆盖原始愿景的一部分，不再宣称完整问题树
  已落地。
- **输出必须显示边界**。`out/问题队列.md` 顶部注明：v1 不包含制造工序、装配接口、正交路线
  覆盖和投资推论问题。
- **后续扩容先 ADR、后发生器**。至少应先确定三类 canonical 结构：
  1. component→process→equipment 制造投影；
  2. component→interface→component 装配接口账本；
  3. 带主张类型、前提、条件、替代方案和证据锚的推论链。
- `route_bom.csv` 已提供产品标准轴、电接口轴、封装架构轴、光子平台轴，可作为未来路线问题
  发生器的数据先例；在覆盖与销号规则定版前，本轮不接入。

这次处置不把聊天中的新研究问题硬塞进 v1，也不让它们丢失：v1 交付一个可信的运营队列，
后续再为完整研究问题空间补 canonical 坐标。
