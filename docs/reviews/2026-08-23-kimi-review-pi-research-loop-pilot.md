## 2. 阻断性批评（P1）

### K1：报告审核了 Pi 的草案，却没有给草案留锚

报告 §2.2、§3 对 KN008–KN010 和 CQ001–CQ005 下了八个定性判断，但通篇没有给出 Pi 会话日志、草案原文或证据包的任何可定位路径（`tmp/` 下只有历史 `pi-brief-se3a/se4` 文件，与本小样无关）。审核人无法复核"把标准目标写成物理极限"等判断是 Pi 真写了这些话，还是报告作者的转述。这正是报告自己在 §3.2 批评 Pi 的同一类问题：结论没有可定位锚。要求：每轮 Pi 产出（合同、原始回答、证据包、草案 YAML、驳回理由）必须先落盘，审核报告逐条引用路径。

—— Kimi（Kimi Code CLI），2026-08-23

### K2：与协作账本和 canonical 边界未对齐

`refs/CODEX-KIMI-COLLAB.md` 列的 canonical 七文件不含 `research_questions.yaml`，而报告把"写入 knowledge.yaml"和"提升到 research_questions.yaml"统称为"写 canonical"，术语不一致。更重要的是，报告 §4 循环图里的"人工批准后写入"没有接入项目已有的治理机制：谁批准、批准记录写在哪、write_scope 怎么认领、谁做 reviewer 验收——这些在协作账本里都有现成协议（工作项 + 单写者 + 消息日志回执），报告却另起了一个未定义的"人工批准"概念。要求：循环的最后一步必须显式映射到账本的工作项/验收流，而不是平行造闸。

—— Kimi（Kimi Code CLI），2026-08-23

### K3：部分"Pi 违规"应归因于研究合同本身，归因错了

小样合同写"只研究 RQ000，同时检查第一层 PQ001、TQ001"，但没有定义"检查"允许什么产出。Pi 起草的 KN010（技术路线为什么分化）从合同字面看就是 TQ001 的答案，并未越界。报告 §3.3 把它定性为"一条 KN 承担太多主张"，掩盖了更准确的结论：合同没有冻结"可读"与"可答"的区分。同样，§3.8 的环境违规也只有"提示词应写死 python 路径"这一条教训，没有检讨合同为什么允许 Pi 自行决定跑校验。下一轮合同必须逐 QID 列出 read/answer 权限，并把"允许执行的命令"写成白名单。

—— Kimi（Kimi Code CLI），2026-08-23

### K4：原子 KN 要求与存量 7 条 KN 冲突，处置方案缺位

报告 §3.3 要求把 KN008 拆成原子条目。但存量 KN001–KN007 本身就是复合叙事条目（KN002 同时含气密定义、电信/数通两条路线分野、结构图解释三段主张），且全部缺少模板要求的 `体系`、`研究问题` 字段。若新循环按原子口径入库，新旧双轨会使问题树的"问题覆盖"统计口径失真；若回头原子化存量，工作量、编号策略（被驳回重写的 KN 编号是否回收）均未讨论。报告必须补充存量处置方案，否则 §6 的两阶段试运行从第一批就会产生口径混杂。

—— Kimi（Kimi Code CLI），2026-08-23

## 3. 非阻断批评（P2/P3）

### K5（P2）：审核报告缺少"本轮验证记录"一节

对照同目录 `2026-08-15-kimi-revenue-lines-review.md` 的体例，审核报告应自带验证命令、执行环境与结果。本文 §2.3 只写"抽查结果"，未说明由谁、在哪个语料快照、用什么命令执行。我已独立重查（见 §1），结论支持报告的抽查，但报告不应依赖下一个审核人重做。

—— Kimi（Kimi Code CLI），2026-08-23

### K6（P2）："只读工具+联网命令"的工具边界与 §3.8 自相矛盾

Pi 能尝试运行系统 Python 并报告"缺 yaml 模块"，说明它实际持有 shell 执行权限——"只读"边界并未真正执行。把 §3.8 定性为"环境约束违规"掩盖了实质问题：工具面授权与合同声明不一致，"只读+联网"是不可校验的表述。应改为命令白名单（如 `curl`/`grep`/`cat` 枚举），让违规可机器判定。

—— Kimi（Kimi Code CLI），2026-08-23

### K7（P2）：5 分钟墙钟预算不可校验、不可复现

网络与模型延迟使同一任务两次运行的墙钟成本差异巨大，"5 分钟无完整结果则停止"无法成为验收标准。建议改为可计数预算：来源族数、检索轮次、产出条目数；墙钟只作兜底。本次"约 4 分钟返回"也无日志可证。

—— Kimi（Kimi Code CLI），2026-08-23

### K8（P2）：方向 A 的"两个来源域"硬门槛对 CPO 等对象可能不可满足

"每个核心对象至少有标准/MSA 和产业主体两个来源域"对标准化主体缺失或口径稀薄的对象（如 CPO 的 MSA 级定义）不可满足，硬门槛会倒逼模型拼凑来源以过闸——正是 §3.4 批评的"schema 合法性替代语义正确性"的翻版。应允许"单来源域 + 缺口显式声明"作为合格态，缺口本身进研究包。

—— Kimi（Kimi Code CLI），2026-08-23

### K9（P2）：§7 问题 5 的研究包选址未考虑 refs/ 上限已满

账本治理快照：`refs_files_in_worktree: 8 / refs_limit: 8`，refs/ 没有余量。Pi 研究包若要版本化，只能新建跟踪目录（如 `research/pi-packages/`）并在 `scan.py` 白名单登记；若放 `tmp/` 则接受不可版本化。报告应给出选址建议，而不是把带约束条件的问题抛回给审核人。

—— Kimi（Kimi Code CLI），2026-08-23

### K10（P3）：CQ 候选与既有 TQ 的覆盖关系未声明

CQ002（800G PMD 组件差异）实质落在 TQ005/TQ010 区间，CQ004（AUI/MDI 通道映射）落在 TQ006/TQ009 区间。若直接发新 CQ 编号而非先作为既有 TQ 的聚焦注记，会造成与主干平行的第二套问题体系，违背问题树"沿研究依赖生长"的原则。建议：子问题默认回填为既有问题的注记，只有确认既有问题验收口径容不下时才发新编号。

—— Kimi（Kimi Code CLI），2026-08-23
